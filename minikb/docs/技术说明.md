# 一页技术说明：端侧向量化 + seekdb 混合检索

**提交形态**：本地启动的 Web 应用（`minikb/`）· **实测设备**：Apple M4 / 16 GB，macOS 26.5，Chromium 156（Playwright 无头，WASM 路径），Node 22.14
**数据规模**：演示库 6–12 条中文短文档；质量评测另用 40 篇文档 + 12 条标注查询（`tests/quality_set.json`）

---

## 1. 模型与量化

| 项 | 内容 |
|---|---|
| 模型 | **Xenova/bge-small-zh-v1.5**（ONNX 版，512 维），原始模型 **BAAI/bge-small-zh-v1.5**，MIT |
| 运行时 | transformers.js **3.8.1** + ONNX Runtime Web **1.22.0-dev.20250409**（wasm 本地 vendor，不走 CDN） |
| 量化方式 | 直接使用官方转换仓库的三种 dtype：fp32 / fp16（半精度）/ int8（`model_quantized.onnx`，8-bit 量化） |

| 指标 | fp32 | fp16 | int8 |
|---|---|---|---|
| 模型体积（同一口径，ONNX 文件） | 90.5 MB | 45.3 MB | **22.9 MB** |
| 压缩比（相对 fp32） | 1.00× | **2.00×** | **3.95×** |
| recall@1 / recall@3 | 1.000 / 1.000 | 未测（CPU 不支持 fp16 推理） | **1.000 / 1.000** |
| 与 fp32 向量余弦一致性 | — | — | 均值 0.9925，最小 0.9895 |
| 单条 embedding（CPU，onnxruntime 4 线程） | 4.1 ms | — | 3.6 ms |

评测方法：`scripts/bench_quality.py` 用同一份 ONNX 文件在 CPU 上做 CLS+L2 编码，语料 40 篇、查询 12 条
（查询措辞刻意与原文不同），按余弦排序统计 recall@1/@3。结果：**INT8 无明显质量损失**，故 WASM 默认 int8；
fp16 留给 WebGPU（体积减半；CPU EP 不支持 fp16 推理，故未做质量对比）。

---

## 2. 端侧运行与后端降级

- 推理链：`text → transformers.js pipeline(feature-extraction) → CLS pooling + L2 → 512 维`，全部在浏览器进程内。
- 后端选择顺序（`public/app.js`）：**WebGPU/fp16 → WebGPU/fp32 → WASM/int8**，每级失败自动落到下一级；
  右上角徽章实时显示「后端：WebGPU/fp16」或「后端：WASM/int8」，`?backend=wasm` 可强制降级用于验证。
- WASM 兜底细节：`ort.env.wasm.wasmPaths` 指向本地 `public/vendor/ort/`（默认走 jsdelivr，国内不可用），
  `numThreads=1` 避免 SharedArrayBuffer/COOP 要求。
- **降级验证**：无头 Chromium 报 `The device (webgpu) does not support fp16`，应用自动切到 `WASM/int8`，
  徽章提示正确，导入/检索全流程通过（见 `docs/e2e-result.json`，0 页面错误）。
- 服务端无任何推理代码路径：`/api/docs` 只接受浏览器算好的向量，集合以 `embeddingFunction: null` 创建；
  模型文件经本机 `/api/hf/*` 代理下载并落盘，不改变推理位置。

## 3. seekdb 使用

**接入**：`seekdb`（seekdb-js）**1.4.0** + `@seekdb/js-bindings` 1.4.0，**嵌入式**模式，数据目录 `data/seekdb`。

**表结构**（每个知识库一张表，`c$v2$<collection_id>`，由 SDK 创建）：

```sql
CREATE TABLE `c$v2$...` (
  `_id` varbinary(512) PRIMARY KEY,
  `document` string,
  `embedding` VECTOR(512),
  `metadata` json,                      -- { title, createdAt }
  FULLTEXT KEY `idx_fts` (`document`) WITH PARSER ik,
  VECTOR KEY `idx_vec` (`embedding`) WITH (DISTANCE=COSINE, TYPE=HNSW, LIB=VSAG, M=16, EF_CONSTRUCTION=200)
) ORGANIZATION HEAP;
```

**三种检索（均在 seekdb 内执行）**：

| 模式 | 实现 | 返回 |
|---|---|---|
| 语义 | `collection.query({queryEmbeddings, approximate:false})` | 相似度 = 1 − 余弦距离 |
| 关键词 | 单条 SQL `MATCH(document) AGAINST(?) ORDER BY score DESC`（IK + BM25） | BM25 相关度 |
| 混合 | **单条 SQL**：两路各 `ROW_NUMBER()` 取前 30 → `UNION ALL` → `SUM(1/(60+rnk))` 融合 → `JOIN` 回表 | RRF 融合分 |

混合检索的融合由数据库一条 SQL 完成，客户端只请求一次、拿一次结果。

**增量写入与刷新**：写入后立即可检索（精确扫描，无索引延迟），实测「点击入库 → 列表可见」中位数 **32 ms**；
`/api/refresh` 保留为维护接口。**偏差说明**：本机构建上 `APPROXIMATE` 查询恒返回空（3/200/1200 条数据均复现，
`refresh_index()` 超时 >120 s，pyseekdb 同样表现），故语义/混合走精确扫描；DDL 中 HNSW 索引保留，
上游修复后把 `approximate` 改回 `true` 即可。

**状态管理**：集合列表来自 `sdk_collections`；当前知识库存 `localStorage`，每次读写/检索都显式带 `collection`，
切换后结果只落在当前集合。

## 4. 状态、优化与性能对比

| 阶段（WASM/int8，5 轮中位数） | 数值 | 备注 |
|---|---|---|
| 模型加载 · 首次（服务端缓存空） | 20.5 s | 24 MB 权重经代理下载，网络瓶颈 |
| 模型加载 · 冷启动（模型已缓存） | **420 ms** | 首次进入页面 |
| 模型加载 · 热启动 | **175 ms** | 刷新页面，浏览器缓存命中 |
| 文档向量化（单条） | **17.8 ms** | min 17.7 / max 18.4 |
| 批量 8 条（每条摊薄） | **17.4 ms** | 相比逐条 18.3×8≈146 ms 提升约 6%（WASM 单线程，收益有限） |
| 写入 → 列表可见 | **32 ms** | 含 embedding + HTTP + seekdb 写入 |
| 查询向量化 | **10 ms** | 短查询 |
| seekdb 检索 | **0.63–1.17 ms**（中位 0.67） | 语义；关键词 1.6 ms / 混合 5.4 ms（首调） |
| 端到端（点击搜索 → 结果渲染） | **30 ms** | 中位 30，min 27 / max 30 |

已做的优化与前后对比：

| 优化 | 优化前 | 优化后 |
|---|---|---|
| 模型文件本机代理 + 磁盘缓存 | 浏览器直连 HF：超时失败 | 首次 20.5 s，二次 6.0 s，三次 0.35–0.42 s |
| wasm/JS 本地 vendor | jsdelivr 连接被重置 | 稳定加载 |
| 批量 embedding | 18.3 ms/条 | 17.4 ms/条 |
| 单条 SQL 完成 RRF | 两路查询 + 客户端合并（2 次往返） | 1 次往返，5.4 ms |
| 写入不阻塞刷索引 | 每次写入阻塞 5 s+ | 32 ms，且立即可查 |


**WebGPU 对照（真机 Chrome 156.0.8078.74 / Apple M4 / `metal-3`，`shader-f16` 可用）**：

| 指标 | WASM/int8 | WebGPU/fp16 |
|---|---|---|
| 单条 embedding | 18.3 ms | **9.3 ms**（7.4–9.8） |
| 批量 8 条（每条摊薄） | 17.6 ms | **2.0–3.6 ms** |
| seekdb 检索 | 1.22 ms | 0.5–3.7 ms |
| 模型加载 | 0.43 s（热） | 6.3 s（含 fp16 shader 编译） |

注意：WebGPU 首轮批处理会触发 fp16 kernel 编译，第一次 8 条要 653 ms（81.7 ms/条），
预热后降到 2–3.6 ms/条。因此应用应在加载后做一次预热推理（代码里已对单条做 warmup，
批处理路径建议首次调用时先跑一小批）。

测试方法遵循赛题 3.2：固定设备/浏览器/语料/查询集；体积按 ONNX 文件实际字节；质量用标注集 recall@K；
分阶段计时；首次与预热分开；每项 5 次取中位数，原始数据见 `docs/bench.json`、`docs/e2e-result.json`。

## 5. 复现

```bash
cd minikb
export PATH="$PWD/../.tools/node/bin:$PATH"        # 或系统 node >= 20
export SEEKDB_BINDINGS_CACHE_DIR="$PWD/.bindings"
npm install --legacy-peer-deps --registry=https://registry.npmmirror.com
./run.sh                                           # 打开 http://127.0.0.1:8787
```

- 质量对比：`../kb/.venv/bin/python scripts/bench_quality.py`（需 onnxruntime、tokenizers）
- 端到端与截图：`PLAYWRIGHT_BROWSERS_PATH=$PWD/.browsers node scripts/e2e.mjs`
- 5 轮性能：`PLAYWRIGHT_BROWSERS_PATH=$PWD/.browsers node scripts/bench.mjs`
- 模型预取（弱网/离线）：应用启动后跑 `scripts/prefetch_model.sh`

## 6. 限制

1. WebGPU 路径已在 Apple M4 + Chrome 156 上实测（后端徽章 `WebGPU/fp16`，adapter `metal-3`）；Windows/独显环境未测。
2. HNSW 索引在当前嵌入式构建未生效（第 3 节偏差说明），万级文档后精确扫描延迟会线性上升。
3. 单进程、无鉴权、只监听 `127.0.0.1`；不支持多 worker 共享数据目录。
4. 长文未切块（`max_position_embeddings=512`），超长文本会被截断。
