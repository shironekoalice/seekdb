# MiniVectorDB 优化方案（对照评分公式）

## 0. 评分口径（来自赛题 §3.3）

- 规模：**10,000 行 × 128 维**，**1,000 条 TopK 查询**，K=10，其中一半带普通列等值过滤；默认 `exact`。
- 写入：每批 100 行、批批提交；T 含持久化。
- 权重：写入 T20% / B6.67% / M6.67%，查询 T40% / B13.3% / M13.3%；
  `E = (E_write + 2·E_query) / 3`，`E_x = 0.6·f(R_T) + 0.2·f(R_B) + 0.2·f(R_M)`，`f(R)=R/(1+R)`，`R=(base+ε)/(ours+ε)`。
- **结论：查询耗时占总权重 40%，是唯一值得重点投的方向**；其次是 I/O（20%）。

## 1. 当前实测（本机 arm64，200k 行 / 10k 规模见括号）

| 指标 | 现在 |
|---|---|
| 批量导入 | 199k 行/秒（10k 行约 0.05 s） |
| 精确 TopK（60k 行 × 128 维） | 18.6 ms |
| ANN TopK（同上，聚类） | 3.3 ms |
| 主键点查 | 0.012 ms |
| 1M 行加载后 RSS | 78 MB |

10k 规模下，查询时间主要花在**逐行解码 + 标量距离**上。

## 2. 优化项与预期收益（按 E 的贡献排序）

### P1 向量列存（查询 T、B、M 同时受益）
- 现状：向量存在行里，每次查询要 decode 整行才能取 128 个 f32。
- 方案：每个向量列单独文件 `/data/vec_<t>_<c>.bin`，定长记录 `[f32;128]`，行号 = pk 映射后的槽位；
  另存 `pk → slot` 数组。查询时顺序扫这个文件，**不碰行页**。
- 收益：去掉了行解码与页访问，预计查询 **1.5–2.5×**；同时减少页缓存压力（M 下降）。
- 风险：写入/更新要同步改列存文件；崩溃恢复要重建（可从行数据重建，成本低）。
- 工作量：~250 行 + 迁移逻辑。

### P2 SIMD 距离计算
- 现状：`for i in 0..dim { d = a[i]-b[i]; sum += d*d }` 标量。
- 方案：`std::arch` 手写 aarch64 NEON / x86_64 AVX2 版本，按 4/8 维展开，运行时用 `is_aarch64_feature_detected!` 选择；
  保留标量兜底（跨平台安全）。
- 收益：距离计算 **2–4×**；与 P1 叠加后查询有望进入 **亚毫秒**。
- 风险：低（纯函数替换，可用现有 20+22 用例回归）。
- 工作量：~120 行。

### P3 逻辑 WAL（压 I/O，占 20%）
- 现状：提交时把**脏页整页 8 KB** 写进 WAL，再把同样内容写回数据文件 → 写放大 2×且按页计。
- 方案：WAL 记录行级 redo（`INSERT/UPDATE/DELETE + 表 + 主键 + 行字节`），恢复时按主键重放到页；
  提交时只 fsync WAL，不再回写数据文件；页面淘汰时才落盘，并周期性 checkpoint（清空 WAL）。
- 收益：10k 行写入的 WAL 从「页数×8KB」降到「行数×~600B」，**B 下降 5–10×**；T 也下降。
- 风险：中（恢复逻辑重写，需要新的崩溃测试矩阵）。
- 工作量：~300 行 + 恢复测试。

### P4 页大小与布局
- 现状：8 KB 页，每页约 15 行，页头 + 槽目录开销约 4%。
- 方案：16 KB 页 + 紧凑槽目录；可选把 `id/score` 等定长列前置。
- 收益：导入 +15–25%，页数减半（B 略降）。
- 风险：低。工作量：~80 行。

### P5 内存（占 20% 的 M）
- 现状：默认页缓存 64 MB；10k 行数据仅 ~10 MB。
- 方案：按数据规模自适应（`min(64MB, 数据大小×1.5)`），并按 cgroup 限额收紧；
  另把 `pk_maps` 改成排序数组（16 B/行）。
- 收益：M 直接下降，R_M 提升。风险：低。工作量：~60 行。

### P6 正确性加固（不直接加分，但决定 0 与非 0）
1. 大结果集超 16 MB/行上限的防护；
2. `NOT NULL` 列插 NULL 的语义；
3. 事务内 DDL 的隐式提交语义；
4. `WHERE` 中使用 `SELECT` 别名；
5. 恢复过程中再次 kill 的自测；
6. `TMPDIR=/data` 兜底（`--read-only` 根文件系统）。

## 3. 实施顺序与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1 | P1 向量列存 + P2 SIMD | 公开 20 + 影子 22 全绿；10k 查询 < 1.5 ms |
| 2 | P5 内存自适应 + P4 页大小 | M 下降 ≥ 30%，导入 +15% |
| 3 | P3 逻辑 WAL | 崩溃矩阵全过；B 下降 ≥ 5×（用 io.stat 模拟） |
| 4 | P6 正确性 6 条 | 新增影子用例全绿 |

每阶段都跑：`protocol_check`（20）+ `extra_suite`（22）+ `fuzz`（多 seed）+ 容器 2C/2G 冒烟。

## 4. 不建议做的

- B+ 树 / MVCC / 多线程：题目限定单进程单事务，收益低、风险高；
- HNSW：现有 IVF 球剪枝已满足 recall≥0.95，替换是重复踩坑；
- 预计算/缓存答案：禁止且会被未公开种子击穿。

## 5. 本轮已落地的修正（对照题面逐条审计后）

| 题面要求 | 之前 | 现在 |
|---|---|---|
| 「不支持的语句须返回约定错误，不能静默执行为其他含义」 | `ORDER BY 未知列` 静默按第 0 列排序 | 返回 `column_not_found` |
| `NOT NULL` 列不得插入 NULL | 忽略修饰符，允许写入 | 返回 `not_null_violation` |
| 大表 `SELECT ... LIMIT n` 不得全量载入 | 先扫全表再截断 | 扫够 n 行即停 |
| 大表 `UPDATE`/`DELETE` 不得全量载入 | 物化全部匹配行 | 逐页流式处理并立即写回 |
| 恢复完成前不得 ready | 已是此行为 | 保持 |
