本轮延续用户的准入优先要求，基于已封存的F03提交
`195bf89d9ad06ee10e842c42d03d3a776118ea44`，只处理独立复现的文件身份问题。
F03逐条要求核对、结果大小/类型/排序修正和负例见 `ADMISSION_AUDIT_F03.md`。
不运行性能benchmark，不正式提测。

## 反例和修复

F03使用SQL表名构造`.pk`、`.flat`和`.pending`文件名。
248字符表名能建表，但第一次INSERT创建`.pending`失败，进程在回应前退出。
260字符表名的CREATE在提交日志同步后创建派生文件失败；随后重启仍不能ready。
原始`fatal: open: File name too long`及协议错误均保存。
这涉及两项要求：支持的名称不能破坏持久化/恢复；不支持输入应返回错误，
不能先提交一个使数据库无法启动的schema。

当前可重建文件使用内部身份：

- 持久表主键映射：`table-<id>.pk`；向量索引：`table-<id>.flat`。
  id按已提交WAL中表的首次创建顺序从0分配，重复schema/index操作保留同一个id。
  不支持DROP，因此重放同一权威日志会得到相同分配，不需要修改WAL或schema格式。
- 事务覆盖层：`pending-<slot>.tmp`，slot按本事务实际创建覆盖映射的顺序分配。
  回滚后复用位置时，原有缓存身份规则仍使不同DiskMap独立。
- 名称不取SQL标识符的截断或散列，没有前缀相同/散列碰撞的别名问题。
  没有增加题包未规定的SQL标识符长度上限。
- `query_order.tmp`在正常查询结束清理，启动恢复前也清理强杀残留；
  它不是权威数据，清理不影响提交状态。

旧日志格式不变。旧派生文件不是恢复依据，新版从同一日志重建内部文件；
旧文件可能留在已有目录中，升级磁盘空间需计入这些残留。
本题每例空目录/同版本重启的行为不依赖旧文件。

## 独立验证设计

`tests/file_identities.py`使用11张表和Python字典作为状态参考：
248/260/1024/4096字符名称、相同300字符前缀但不同后缀的名称、
以及类似内部文件的普通名称。创建顺序故意与字典序不同，
验证普通行和向量TopK、多表更新/删除/插入、回滚、提交后强杀、
重复正常重启、新建表回滚后复用名称与覆盖文件。

同一个工具在F03二进制实际失败，在候选版本验证。
原生Release和Sanitizer还把**旧版失败后留下的同一目录**交给新版，
检查已提交的短表数据/向量索引仍正确、未回应但已完整记录的长表可恢复，
之后可插入并再次强杀恢复。

排序清理通过真实退出点验证：写入4096字节排序键后实际exit86，
确认文件确实残留，重启后在查询前已消失；重新排序结果正确并清理文件。
不是只检查清理函数是否被调用。

原`storage_namespace.py`的SQL和独立状态断言保留；
其诊断读取路径增加内部`table-1.pk`支持，旧版本仍读取`statement.pk`。
这仅调整内部结构取证，未删除历史F02反例或放宽断言。
F03工具曾把最终两行JSON大小说明写成11字节，实际是13字节；
F04改为从独立预期数组实际序列化计数。旧报告和原工具按原样保留，
这个说明修正不改变任何SQL断言或旧版失败结果。
