## 已复现并修正的差异

| 问题 | 旧版实际表现 | 修正 |
|---|---|---|
| 按中间候选投影大小拒绝TopK | 两个最初候选各8MiB，最终胜出的两行只有`a`、`b`，仍报resource_limit | 先完成TopK，再按当前可见主键读取最终投影 |
| 自设15MiB结果上限 | 15,761,460字节的合法响应被拒绝，而公开上限为16,777,216字节 | 按最终结果及完整响应实际UTF-8字节数限制；包含换行，超一字节返回错误 |
| 普通宽字符串排序持有全量键 | 128MiB内存、256MiB活跃正文，`SELECT id ... ORDER BY body LIMIT 4096`触发OOM；结果本应只有4096个ID | 长于256字节的排序键暂存`/data/query_order.tmp`，按8KiB块比较；查询结束清理 |
| 反引号标识符被当成常量 | ``INSERT ... VALUES(1,`2`,'[0]')``被当作写入数字2并成功 | 保留标识符Token类型，标量/向量字面量拒绝标识符；反引号关键字列名可正常投影 |
| 未发布的字段声明上限 | `VARCHAR(100000001)`即使只存`small`也无法建表 | 删除100000000这个人为上限，保留正整数及BIGINT解析约束 |
| 未发布的64MiB单行日志上限 | 67,109,888字节合法正文写入被拒绝 | 使用既有uint32帧长度格式的自然上限；恢复仍检查实际文件边界、校验和与commit marker |

后两项是移除题包未规定的人为边界；不声称隐藏用例一定覆盖它们。
日志格式未改变，旧版有效日志仍可读取；新大帧不保证被旧实现读取。
崩溃模型仍仅为进程终止，不扩展为断电或外部文件损坏。

## 未发布或需明确的边界

以下是公开契约信息不足，不把猜测当作代码错误，也不擅自扩大SQL方言：

- 没有提供完整冻结的SQL文法。当前支持列内主键；表级PRIMARY KEY、NOT NULL、
  DEFAULT、表别名、ORDER BY序号、块注释、Unicode标识符等额外写法不承诺支持。
  未支持写法必须返回错误。
- 未公开明确规定列名大小写显示、跨表索引重名、UPDATE赋相同值的计数口径，
  以及无ORDER BY但带LIMIT的固定子集。当前标识符归一化小写、索引名全局唯一、
  affected_rows按匹配记录数；无ORDER时给出主键顺序的确定结果。
- 公开配置给出2CPU/2GiB、120秒启动、60秒请求、600秒普通用例和16MiB响应，
  未提供完整磁盘/I/O/向量维度/K冻结范围。不能用自行放宽时限替代验证。
- float32转换继续检查输入不超过有限float32数值范围；公开包没有规定范围外但可舍入
  回最大有限值的临界十进制输入口径，没有据此改动已有类型规则。
- WAL仍重放完整历史、未做checkpoint/回收；固定哈希桶在极端长链下也可能慢。
  这是资源与超时风险，需要实际数据规模或日志继续判断，本轮不据猜测做性能改造。
- 查询强杀时可能残留排序临时文件；它不作为恢复权威，下一次宽排序会截断重用。
  每条宽排序的临时写入最多随被检查的排序键总字节数增长，磁盘预算仍需真实冻结配置核对。
- Agent材料明确缺少学生自身对数据库机制的完整解释；格式通过不能保证学习排名分。

## 本轮验证

本轮12个计划阶段全部通过：Docker公开20/扩展5、Sanitizer公开20/扩展11、
独立查询119次、点查询1218次/范围对照812次/错误反例90次、六表名回归，
以及六项新增边界。40份实际Sanitizer日志未发现报告。
完整宽排序检查的活跃正文为2,415,919,104字节、内存上限2,147,483,648字节，
实际swap.max=0、host换页增量0、无OOM；全部检查215.850秒，
其中主排序请求30.042秒，低于未修改的60秒请求时限。这些数字不是性能E。

继续检查时另发现**尚未在F03修复的严重问题**：表名直接成为文件名。
248字符表名建表成功但INSERT退出；260字符表名建表退出，重启也失败，
因为已经持久化的schema无法创建派生文件。见`long-names-control.json`与原始stderr。
F03只封存已验证修复，接着独立进行F04；不能把本版本称为已无已知准入问题。
